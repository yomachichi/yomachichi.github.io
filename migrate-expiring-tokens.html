Migrating a Shopify Express app to expiring offline tokens: a checklist

Public apps must stop using non-expiring offline access tokens on the GraphQL Admin API by January 1, 2027. On Express, the new flag does not touch your existing installs. Here is what we saw when we migrated a real install on a development store, and an order of steps that survives failure.

Updated 2026-10-24. Every observed result below is from one development store with one test app (legacy install flow, scope read_products). Nothing here was run on a production store.

The deadline in one paragraph

In Shopify's words: "New public apps already can't use non-expiring tokens, and existing public apps can't after January 1, 2027." After that date a GraphQL Admin API call made with an old token gets 403 Forbidden, with an error containing Non-expiring access tokens are no longer accepted for the Admin API. Custom and merchant-created apps are not affected. (Shopify docs)

The new token model

An expiring offline access token lives about an hour (expires_in 3600). It comes with a refresh token that lives 90 days (refresh_token_expires_in 7776000). Every refresh returns a new pair. The refresh token you just used stays valid until you use its successor, or for 30 days after its first use, or until its own 90-day expiry, whichever comes first. A 401 {"error":"invalid_request"} on refresh is final: the merchant has to re-authenticate. Network errors, timeouts, 5xx and 429 are safe to retry with the same refresh token. Shopify also says to "refresh one store at a time". (offline tokens, refresh)

The Express gap: the flag skips existing installs

@shopify/shopify-app-express 8.0.0 added a future flag:

shopifyApp({ ..., future: { expiringOfflineAccessTokens: true } })

With it on, the OAuth callback requests an expiring token, validateAuthenticatedSession refreshes a token that is expired or within 5 minutes of expiring, and shopify.ensureValidOfflineSession(shop) does the same for work that never passes through a merchant request (webhooks, cron jobs, queues). It throws if the flag is off, so a misconfigured app fails loudly.

The catch is in the same CHANGELOG entry: "Existing installs keep their current non-expiring token until the next OAuth", and "ensureValidOfflineSession will not upgrade a non-expiring token either". A shop that installed your app a year ago and never opens it again keeps its old token, and on January 1 every background call for that shop starts failing. Those are often your quietest, longest-paying customers.

  • 8.0.0 requires Node.js 22 or later.
  • Upgrade at least to shopify-app-express 8.0.1 / shopify-api 14.0.1. Before that patch, with debug logging on, the request body of OAuth token calls was written to the debug log, and those requests carry your client secret and tokens.

(CHANGELOG)

The one-time migration exchange

Existing installs need a one-time token exchange that turns the stored non-expiring token into an expiring pair, without a merchant session: a form-encoded POST to https://{shop}/admin/oauth/access_token with

grant_type           = urn:ietf:params:oauth:grant-type:token-exchange
client_id, client_secret
subject_token        = <the stored non-expiring token>
subject_token_type   = urn:shopify:params:oauth:token-type:offline-access-token
requested_token_type = urn:shopify:params:oauth:token-type:offline-access-token
expiring             = 1

@shopify/shopify-api wraps this as shopify.auth.migrateToExpiringToken since 12.2.0. (docs)

What a real store returned

  1. A brand-new app can still get a non-expiring token. The code exchange without expiring=1 returned only access_token and scope, and that token answered GraphQL with 200. (Our app had no distribution chosen, which may be why.) Send expiring=1 on every code exchange.
  2. The migration exchange returned 200 with expires_in 3599, a refresh_token and refresh_token_expires_in 7775999.
  3. The old token died immediately, and not with the documented error. Right after the exchange the old token got 401 "[API] Invalid API key or access token" on GraphQL and REST, not the 403 phrase. If the write of the new pair fails, you now hold a token that no longer works.
  4. A lost response is recoverable. Repeating the exact same exchange returned the same pair, with expires_in counting down. Keep the old token until the new pair is safely stored: it is the key you need to repeat the request.
  5. Lifetimes are time left, not constants. Store expires_at = now + expires_in as given, and treat 0 or less as "already expired", not "missing".
  6. Refresh rotation behaved as documented. The first refresh token, presented after its successor had been used, got 401 "This request requires an active refresh_token". An earlier access token kept working until its own expiry.

A migration order that survives failure

  1. Upgrade (Node 22, shopify-app-express 8.0.1+), turn the flag on, deploy. New installs now get expiring tokens.
  2. Check your session storage really persists refreshToken and refreshTokenExpires. Read a row back after a test write.
  3. Dry run: list every offline session (offline_{shop}) with no refresh token. No network calls, no writes. Compare the count with your install count.
  4. Migrate one shop at a time: exchange, then write the new fields onto the same session row, keeping every other field. Never delete first and insert second.
  5. Record a result per shop: migrated / already expiring / no session / failed. A 400 invalid_subject_token usually means revoked or uninstalled; record it and move on.
  6. Refuse to post your client secret to anything that is not <name>.myshopify.com.
  7. Run it twice. The second run should make no exchange calls.

Background work and webhooks

  • Load sessions in webhooks, cron jobs and queues through ensureValidOfflineSession (or a refresh-if-due wrapper), never by reading the stored token directly.
  • Refresh single-flight per shop. Two workers refreshing the same shop at once retire each other's refresh token. Across instances you need a shared lock (Redis, a Postgres advisory lock).
  • Retry an Admin API call once after a 401: refresh, then retry. A second 401 means re-authenticate.
  • If a refresh response arrives without expires_in, don't store it as non-expiring (shopify-app-js #3400).
  • Uninstall and compliance webhooks often arrive when the token is already gone. Verify the HMAC, then answer 200 when the only failure is a missing session, or Shopify keeps retrying (#3360).

The checklist

  • Node 22 and shopify-app-express 8.0.1+ (or shopify-api 14.0.1+), debug token logging off in production
  • Flag on; one fresh install on a dev store gets an expiring token
  • Session storage round-trips refreshToken / refreshTokenExpires
  • Every background caller loads sessions through a refresh-if-due path
  • Per-shop single-flight refresh, with a shared lock if you run more than one instance
  • Migration: dry run, one shop at a time, write-then-retire, per-shop report, second run is a no-op
  • Uninstall and compliance webhooks answer 200 on "no session" after HMAC verification
  • Alerting on the 403 "Non-expiring access tokens are no longer accepted" phrase after January 1

Do it on a development store first: install through the old flow so it holds a real non-expiring token, migrate it, and watch the old token stop working and the new one keep working. That one run caught a bug that our tests against a fake never did.
